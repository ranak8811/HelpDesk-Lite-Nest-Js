# ০৭. ইনফ্রাস্ট্রাকচার ও পাবলিক ডেপ্লয়মেন্ট: লোকালহোস্ট থেকে ক্লাউড সার্ভার

প্রজেক্টের ঠিক এই পর্যায়ে টিউটোরিয়ালে একটি চমৎকার ইঞ্জিনিয়ারিং সিদ্ধান্ত নেওয়া হয়েছিল: **পুরো প্রজেক্ট শেষ হওয়া পর্যন্ত অপেক্ষা না করে, মাঝপথেই অ্যাপ্লিকেশনটিকে একটি লাইভ পাবলিক সার্ভারে ডেপ্লয় করে দেখা।** 

কেন এমন সিদ্ধান্ত? এবং প্রোডাকশন ইনফ্রাস্ট্রাকচারে কোড কীভাবে রান করে, তা এই অধ্যায়ে বিস্তারিত আলোচনা করা হলো।

---

## ১. ইঞ্জিনিয়ারিং মাইন্ডসেট: কেন মাঝপথে ডেপ্লয়মেন্ট?

অধিকাংশ শিক্ষার্থী প্রজেক্টের সব কোড শেষ করার পর ডেপ্লয় করতে গিয়ে আটকে যান—তখন পোর্ট এরর, বিল্ড এরর নাকি প্যাকেজ এরর, তা খুঁজে পাওয়া কঠিন হয়ে পড়ে।
- প্রাথমিক কন্ট্রোলার, সার্ভিস ও ভ্যালিডেশন দাঁড়িয়ে যাওয়ার সাথে সাথেই ক্লাউড সার্ভারে বিল্ড করে দেখা উচিত পাইপলাইন ঠিকঠাক কাজ করছে কি না।
- এতে কনফিডেন্স তৈরি হয় এবং রিয়েল এনভায়রনমেন্টের সীমাবদ্ধতাগুলো আগেভাগেই ধরা পড়ে।

---

## ২. বিল্ড প্রসেসের মূল সত্য (`dist/main.js`)

লোকাল কম্পিউটারে আমরা টার্মিনালে লিখি:
```bash
npm run start:dev
```
নেস্ট নিজে ফাইলগুলো মেমোরিতে ট্র্যাক করে সার্ভার চালায়। **কিন্তু প্রোডাকশন সার্ভার কখনোই সরাসরি TypeScript ফাইল চালাতে পারে না!**

### প্রোডাকশনে কী ঘটে?
1. হোস্টিং সার্ভার (যেমন: Hostinger, AWS, DigitalOcean) গিটহাব থেকে আপনার কোড নিয়ে চালায়:
   ```bash
   npm install      # সব ডিপেনডেন্সি ইনস্টল করে
   npm run build    # TypeScript কোড কম্পাইল করে dist/ ফোল্ডারে জাভাস্ক্রিপ্ট বানায়
   ```
2. সার্ভারের মূল এন্ট্রি পয়েন্ট হলো **`dist/main.js`**। নোড ইঞ্জিন এই জাভাস্ক্রিপ্ট ফাইলটি চালিয়েই আপনার ব্যাকএন্ড সচল রাখে।

> 📌 **মনে রাখুন:** গিটহাবে কখনোই `node_modules/` বা `dist/` পুশ করতে হয় না। সার্ভার স্বয়ংক্রিয়ভাবে সোর্স কোড থেকে ফ্রেশ বিল্ড তৈরি করে নেয়।

## ৩. ডাইনামিক পোর্ট স্ট্র্যাটেজি (`process.env.PORT`)

[src/main.ts](../../src/main.ts)-এর শেষ লাইনটি একটু খেয়াল করুন:

```typescript
await app.listen(process.env.PORT ?? 3000);
```

এই ছোট্ট লাইনটি সফটওয়্যার ইঞ্জিনিয়ারিংয়ের একটি লাইফসেভার!

### কেন এটি জরুরি?
- আপনার লোকাল মেশিনে আপনি মুক্তভাবে পোর্ট `3000`-এ অ্যাপ্লিকেশন চালাতে পারেন।
- কিন্তু ক্লাউড বা হোস্টিং সার্ভারে একই সার্ভারে শত শত অ্যাপ্লিকেশন চলতে পারে। সেখানে হোস্টিং ইনফ্রাস্ট্রাকচার নিজে নির্ধারণ করে দেয় আপনার অ্যাপ কোন পোর্টে চলবে, এবং সেই পোর্টটি `PORT` নামক এনভায়রনমেন্ট ভেরিয়েবলে পাঠিয়ে দেয়।
- আমাদের কোডে `process.env.PORT ?? 3000` লেখার কারণে:
  - সার্ভারে পোর্ট সেট করা থাকলে অ্যাপ স্বয়ংক্রিয়ভাবে সেই পোর্টে রান করবে।
  - লোকাল মেশিনে পোর্ট না থাকলে ফলব্যাক হিসেবে `3000` ব্যবহার করবে।
- এক লাইন কোডও পরিবর্তন না করে অ্যাপ লোকালহোস্ট ও লাইভ সার্ভার উভয়েই চলতে পারে।

## ৪. ইন-মেমোরি ডেটার বাস্তবতা ও সার্ভার রিস্টার্ট

লাইভ সার্ভারে টেস্ট করার সময় অনেকেই একটি বিষয়ে বিভ্রান্ত হন:
> *"আমি নতুন একটি টিকিট তৈরি করলাম, কিন্তু প্রজেক্ট রি-ডেপ্লয় বা সার্ভার রিস্টার্ট করার পর সেই টিকিটটি উধাও হয়ে গেল কেন?"*

### এটি কোনো বাগ বা হোস্টিং সমস্যা নয়!
- আমাদের টিকিটগুলো জমা আছে নোডজেএস প্রসেসের **র‍্যামে (In-Memory Array)**।
- যখনই সার্ভার রিস্টার্ট হয় বা নতুন ভার্সন রি-ডেপ্লয় হয়, পুরোনো নোড প্রসেসটি বন্ধ হয়ে সম্পূর্ণ নতুন একটি প্রসেস চালু হয়।
- ফলে মেমোরি খালি হয়ে যায় এবং আমাদের কোডে থাকা ৩টি প্রাথমিক সিড টিকিট আবার নতুন করে লোড হয়।
- **বাস্তব সমাধান:** প্রোডাকশনে ডেটা টিকে রাখার জন্য এক্সটার্নাল ডেটাবেজ (PostgreSQL, MongoDB) ব্যবহার করা হয়, যা সার্ভার প্রসেসের বাইরে নিরাপদে সংরক্ষিত থাকে।
