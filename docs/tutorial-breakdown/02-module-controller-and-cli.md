# ০২. মডিউল, কন্ট্রোলার ও CLI ফিলোসফি

এই অধ্যায়ে আমরা শিখবো কীভাবে Nest CLI দিয়ে সুশৃঙ্খলভাবে ফিচার মডিউল এবং কন্ট্রোলার তৈরি করতে হয়, এবং কেন প্রতিটি ফাইলের অবস্থান আর্কিটেকচারের জন্য অত্যন্ত গুরুত্বপূর্ণ।

---

## ১. Nest CLI কমান্ড ও ফ্ল্যাগের রহস্য (`--flat` এবং `--no-spec`)

Nest CLI কোড জেনারেশনকে অত্যন্ত দ্রুত করে। তবে নতুনরা প্রায়ই সিএলআই-এর ডিফল্ট আচরণের কারণে ফোল্ডার স্ট্রাকচার এলোমেলো করে ফেলেন।

### ক) `--flat` ফ্ল্যাগ কেন জরুরি?
ডিফল্টভাবে Nest CLI যেকোনো উপাদান জেনারেট করার সময় তার নিজের নামে আলাদা একটি সাব-ফোল্ডার বানিয়ে ফেলে।
- যেমন: আপনি যদি লেখেন `nest g interface tickets/ticket`, সিএলআই তৈরি করবে: `src/tickets/ticket/ticket.interface.ts` (অপ্রয়োজনীয় ডুপ্লিকেট ফোল্ডার)।
- কিন্তু `--flat` দিলে সে কোনো নতুন সাব-ফোল্ডার তৈরি না করে সরাসরি মূল ফোল্ডারে ফাইলটি রাখে: `src/tickets/ticket.interface.ts`।

### খ) `--no-spec` ফ্ল্যাগ কেন জরুরি?
- ডিফল্টভাবে প্রতিটা ফাইলের সাথে একটি করে টেস্টিং ফাইল (`*.spec.ts`) জেনারেট হয়।
- যখন আপনি দ্রুত প্রজেক্ট বানাচ্ছেন এবং অটোমেটেড টেস্ট লিখছেন না, তখন `--no-spec` ফ্ল্যাগ দিলে অপ্রয়োজনীয় টেস্ট ফাইলগুলো তৈরি হয়ে প্রজেক্ট ভারী হয় না।

---

## ২. ফিচার বাউন্ডারি: `TicketsModule` তৈরি

টার্মিনালে কমান্ড:
```bash
nest g module tickets
```
*(সংক্ষিপ্ত রূপ: `nest g mo tickets`)*

### পর্দার পেছনে কী ঘটলো?
1. `src/tickets/tickets.module.ts` ফাইলটি তৈরি হলো।
2. Nest CLI নিজে স্বয়ংক্রিয়ভাবে [src/app.module.ts](../../src/app.module.ts) ফাইলে গিয়ে `TicketsModule`-কে `imports`-এর তালিকায় যুক্ত করে দিলো:
   ```typescript
   @Module({
     imports: [TicketsModule],
   })
   export class AppModule {}
   ```

### 💡 ইঞ্জিনিয়ারিং ভাবনা: Feature Boundary কী?
- সব ফিচারকে যদি `AppModule`-এর ভেতর ঠুসে রাখা হতো, তাহলে কয়েক মাস পর কোডবেজ বোঝা অসম্ভব হয়ে যেত।
- `TicketsModule` হলো টিকিট ফিচারের একটি সুনির্দিষ্ট **বাউন্ডারি (সীমানা)**। টিকিটের কন্ট্রোলার, সার্ভিস ও ডোমেন লজিক শুধু এর ভেতরেই থাকবে। রুট মডিউল শুধু জানবে যে অ্যাপ্লিকেশনে টিকিট নামে একটি স্বয়ংসম্পূর্ণ ফিচার আছে।

---

## ৩. গ্লোবাল প্রিফিক্স স্ট্র্যাটেজি (`main.ts`)

আমরা চাই আমাদের প্রতিটি API রুট `/api` দিয়ে শুরু হোক (যেমন: `/api/tickets`)।

### সাধারণ কিন্তু খারাপ উপায়:
কন্ট্রোলারের মাথায় গিয়ে লেখা `@Controller('api/tickets')`।
- *সমস্যা:* অ্যাপ্লিকেশনে ২০টি কন্ট্রোলার থাকলে ২০ জায়গাতেই ম্যানুয়ালি `api/` লিখতে হবে। কালকে যদি ভার্সন পরিবর্তন হয়ে `/api/v1` করতে হয়, তবে ২০টি ফাইলে গিয়ে হাত দিতে হবে!

### ✅ প্রফেশনাল ইঞ্জিনিয়ারিং উপায়:
[src/main.ts](../../src/main.ts)-এ অ্যাপ্লিকেশন তৈরি হওয়ার সাথে সাথে গ্লোবাল প্রিফিক্স বসিয়ে দেওয়া:

```typescript
// src/main.ts
const app = await NestFactory.create(AppModule);

app.setGlobalPrefix('api'); // ⬅️ পুরো অ্যাপ্লিকেশনের সব রাউটের আগে স্বয়ংক্রিয়ভাবে /api বসবে

await app.listen(process.env.PORT ?? 3000);
```
এখন প্রতিটি কন্ট্রোলার শুধুমাত্র তার নিজস্ব রিসোর্স পাথ (যেমন `@Controller('tickets')`) লিখবে, আর ফাইনাল ইউআরএল এমনিতেই দাঁড়িয়ে যাবে: `/api/tickets`।

## ৪. প্রথম কন্ট্রোলার তৈরি ও রুট হ্যান্ডলার

টার্মিনালে কমান্ড:
```bash
nest g controller tickets --no-spec
```

CLI স্বয়ংক্রিয়ভাবে [src/tickets/tickets.module.ts](../../src/tickets/tickets.module.ts)-এর `controllers` লিস্টে `TicketsController`-কে যুক্ত করে দেবে।

### কন্ট্রোলারে প্রথম এন্ডপয়েন্ট লেখা:
```typescript
// src/tickets/tickets.controller.ts
import { Controller, Get } from '@nestjs/common';

@Controller('tickets') // রাউট প্রিফিক্স: /tickets
export class TicketsController {
  
  @Get() // GET /api/tickets
  findAll() {
    return []; // আপাতত একটি খালি অ্যারে ফেরত দেওয়া হচ্ছে
  }
}
```

### স্টার্টার বয়লারপ্লেট রিমুভ করা:
এখন যেহেতু আমাদের নিজস্ব ফিচার কন্ট্রোলার কাজ করছে, তাই স্টার্টার প্রজেক্টের ডিফল্ট `src/app.controller.ts` এবং `src/app.service.ts` ডিলিট করে দেওয়া হয়। রুট `AppModule`-এ এখন আর কোনো কন্ট্রোলার বা প্রোভাইডার থাকবে না—সে শুধু ফিচার মডিউলগুলোকে ধারণ করবে।

### টেস্ট করা (Postman):
- **Method:** `GET`
- **URL:** `http://localhost:3000/api/tickets`
- **Response:** `[]` (Status: `200 OK`)

আমাদের রিকোয়েস্ট সফলভাবে গ্লোবাল প্রিফিক্স ও কন্ট্রোলারের মধ্য দিয়ে সঠিক মেথডে পৌঁছে গেছে!
