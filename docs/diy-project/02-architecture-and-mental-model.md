# 02. Architecture and Mental Model (আর্কিটেকচার এবং মানসিক ফ্রেমওয়ার্ক)

যেকোনো সফটওয়্যার অ্যাপ্লিকেশন কোড লেখার আগে সবচেয়ে গুরুত্বপূর্ণ ধাপ হলো—**সিস্টেমের মানসিক ছবি (Mental Model) এবং আর্কিটেকচার পরিষ্কার রাখা**। 

তুমি যদি আর্কিটেকচার না বুঝে সরাসরি কোড লেখা শুরু করো, তবে প্রতিটি ধাপে গিয়ে দ্বিধায় পড়বে: "এই লজিকটা কি কন্ট্রোলারে রাখবো নাকি সার্ভিসে?", "ভ্যালিডেশন কি DTO করবে নাকি Service-এ `if-else` লিখবো?", "অ্যাডমিন চেক কোথায় বসবে?"।

এই গাইডে আমরা **EventPulse-Lite**-এর সম্পূর্ণ আর্কিটেকচার এবং নেস্টজেএস রিকোয়েস্ট লাইফসাইকেল ভেতর থেকে বিশ্লেষণ করবো।

---

## ১. NestJS Request Lifecycle: একটি রিকোয়েস্টের পূর্ণাঙ্গ ভ্রমণ

ধরা যাক, ক্লায়েন্ট (Postman/Frontend) থেকে একটি রিকোয়েস্ট এলো:
```http
PATCH /api/events/2/cancel
Headers:
  x-admin-key: organizer-secret-key
```

এই রিকোয়েস্টটি সার্ভারে আসার পর কীভাবে বিভিন্ন লেয়ারের মধ্য দিয়ে ভ্রমণ করে তা নিচের চিত্রে দেখে নেওয়া যাক:

```
[ Client Request ]
       │
       ▼
 ┌─────────────┐
 │ Middleware  │ ──> Logging (HTTP Method, Path, Timestamp)
 └──────┬──────┘
        ▼
 ┌─────────────┐
 │    Guard    │ ──> Authentication / Secret Key চেক (যদি ব্যর্থ হয় -> 403 Forbidden)
 └──────┬──────┘
        ▼
 ┌─────────────┐
 │    Pipe     │ ──> Param Parsing (string '2' -> number 2) & DTO Validation
 └──────┬──────┘
        ▼
 ┌─────────────┐
 │ Controller  │ ──> শুধুমাত্র রিকোয়েস্ট রিসিভ ও সার্ভিসের মেথড কল
 └──────┬──────┘
        ▼
 ┌─────────────┐
 │   Service   │ ──> আসল বিজনেস লজিক (ইভেন্ট আছে কি? সিট খালি কি? স্ট্যাটাস পরিবর্তন)
 └──────┬──────┘
        ▼
 ┌─────────────┐
 │ Interceptor │ ──> রেসপন্স ফরম্যাটিং (wrap into { success: true, data })
 └──────┬──────┘
        ▼
[ Client Response ]
```

## ২. প্রতিটি লেয়ারের দায়িত্ব বণ্টন (Separation of Concerns)

সফটওয়্যার ইঞ্জিনিয়ারিংয়ের অন্যতম প্রধান নীতি হলো **Single Responsibility Principle (SRP)**। প্রতিটি লেয়ারের কেবল একটি নির্দিষ্ট কাজ থাকা উচিত:

### ক. Middleware (গেটকিপার ও অবজারভার)
* **কাজ:** রিকোয়েস্ট আসার সাথে সাথে সবার আগে এক্সিকিউট হয়।
* **EventPulse-Lite এ এর ব্যবহার:** রিকোয়েস্টের লগিং (`Method`, `URL`, `Timestamp`) করা।
* **কী করবে না:** কোনো বিজনেস লজিক বা পারমিশন চেক করবে না।

### খ. Guard (নিরাপত্তারক্ষী)
* **কাজ:** রিকোয়েস্টকারী কি এই অ্যান্ডপয়েন্ট ব্যবহারের যোগ্য? `true` দিলে রিকোয়েস্ট ভেতরে যাবে, `false` দিলে সাথে সাথে `403 Forbidden` রিটার্ন করবে।
* **EventPulse-Lite এ এর ব্যবহার:** `AdminGuard` যা চেক করবে হেডারে `x-admin-key: organizer-secret-key` আছে কি না।
* **কী করবে না:** ডেটা ভ্যালিডেশন বা ডেটাবেজ মডিফিকেশন করবে না।

### গ. Pipe (ডেটা ট্রান্সফরমার ও ভ্যালিডেটর)
* **কাজ:** ইনকামিং ডেটাকে টাইপ কাস্ট করা (যেমন: URL প্যারামের `"2"` স্ট্রিংকে `2` নাম্বারে রূপান্তর) এবং DTO অনুসারে ডেটার গঠন ভ্যালিডেট করা।
* **EventPulse-Lite এ এর ব্যবহার:** `ParseIntPipe` (আইডি কনভার্সন) এবং গ্লোবাল `ValidationPipe`।
* **কী করবে না:** বিজনেস লজিক চেক (যেমন: "সিট খালি আছে কি না") পাইপে হবে না।

### ঘ. Controller (ট্রাফিক পুলিশ)
* **কাজ:** ইনকামিং রিকোয়েস্টকে সঠিক সার্ভিসের মেথডে পাঠানো এবং আউটপুট ফেরত দেওয়া।
* **গোল্ডেন রুল:** কন্ট্রোলার হবে একদম **স্লিম (Skinny Controller)**। এখানে কোনো `if-else` বিজনেস ডিসিশন থাকবে না।

### ঙ. Service (বিজনেস ব্রেইন)
* **কাজ:** সিস্টেমের সম্পূর্ণ বিজনেস লজিক বহন করা। 
  - ইভেন্টটি ডেটাতে আছে কি না? না থাকলে `NotFoundException` থ্রো করা।
  - ইভেন্টটি কি ইতিমধ্যে ক্যান্সেল হয়ে গেছে? হ্যাঁ হলে `BadRequestException` থ্রো করা।
  - সিট সংখ্যা ঠিকমতো আপডেট করা।
* **গোল্ডেন রুল:** সার্ভিস থাকবে ফ্রেমওয়ার্ক-অ্যাগনস্টিক। অর্থাৎ এটি কোনো HTTP রিকোয়েস্ট/রেসপন্স অবজেক্টের ওপর নির্ভরশীল হবে না।

### চ. Interceptor (পোস্টম্যান / রেসপন্স ডিজাইনার)
* **কাজ:** কন্ট্রোলার থেকে তৈরি হওয়া রেসপন্স ক্লায়েন্টের কাছে যাওয়ার ঠিক আগ মুহূর্তে তাকে পরিবর্তন বা মোড়কবদ্ধ (Format/Wrap) করা।
* **EventPulse-Lite এ এর ব্যবহার:** সব সফল রেসপন্সকে `{ success: true, data: ... }` ফরম্যাটে র‍্যাপ করা।

## ৩. ডিরেক্টরি স্ট্রাকচার ব্লুপ্রিন্ট (Clean Modular Structure)

তোমার প্রোজেক্টের ফোল্ডার স্ট্রাকচার কেমন হওয়া উচিত, তার একটি পেশাদার ব্লুপ্রিন্ট:

```text
eventpulse-lite/
├── src/
│   ├── common/                       # পুরো অ্যাপে পুনর্ব্যবহারযোগ্য আর্কিটেকচারাল কম্পোনেন্ট
│   │   ├── guards/
│   │   │   └── admin.guard.ts        # x-admin-key ভ্যালিডেশনের গার্ড
│   │   ├── interceptors/
│   │   │   └── response.interceptor.ts # রেসপন্স র‍্যাপার
│   │   └── middleware/
│   │       └── request-logger.middleware.ts # ইনকামিং রিকোয়েস্ট লগার
│   │
│   ├── events/                       # Events ফিচার মডিউল
│   │   ├── dto/
│   │   │   ├── create-event.dto.ts
│   │   │   ├── update-event.dto.ts
│   │   │   └── filter-events-query.dto.ts
│   │   ├── interfaces/
│   │   │   └── event.interface.ts    # Event ও তার Enum এর টাইপ ডেফিনিশন
│   │   ├── events.controller.ts      # রাউটিং অ্যান্ডপয়েন্টস
│   │   ├── events.service.ts         # ইন-মেমোরি অ্যারে ও লজিক
│   │   └── events.module.ts          # ফিচার মডিউল কনফিগারেশন
│   │
│   ├── app.module.ts                 # রুট মডিউল (EventsModule এবং Middleware রেজিস্ট্রি)
│   └── main.ts                       # বুটস্ট্র্যাপ ফাইল (Global Pipe & Interceptor)
├── tsconfig.json                     # ডেকোরেটর এবং ক্লাস ফিল্ড কনফিগারেশন
└── package.json
```

## ৪. স্টেট ম্যানেজমেন্ট ও ইন-মেমোরি আর্কিটেকচার

যেহেতু এই ফেজে কোনো রিয়েল ডেটাবেজ (PostgreSQL/MongoDB) ব্যবহার করা হচ্ছে না, তাই ডেটা রাখা হবে **ইন-মেমোরি স্টেট (In-Memory State)** হিসেবে:

1. **Service এর প্রাইভেট প্রপার্টি:** `EventsService`-এর মধ্যে একটি প্রাইভেট অ্যারে থাকবে: `private events: Event[] = [...]`।
2. **আইডি জেনারেশন কৌশল:** নতুন ইভেন্ট যুক্ত করার সময় অ্যারিতে থাকা সর্বোচ্চ আইডির চেয়ে ১ বেশি (`max(id) + 1`) অথবা একটি কাউন্টার ভেরিয়েবল ব্যবহার করবে।
3. **ইমিউটেবিলিটি বনাম মিউটেবিলিটি:**
   - ডেটা খোঁজার জন্য: `.find()` বা `.filter()`।
   - আপডেট করার জন্য: অবজেক্টের রেফারেন্স মিউটেট না করে অবজেক্ট স্প্রেড (`{ ...event, ...updateDto }`) করে আপডেট করা উত্তম প্র্যাকটিস।

## ৫. ডিপেন্ডেন্সি ইনজেকশন (Dependency Injection) মানসিকতা

NestJS-এর মূল শক্তি হলো Inversion of Control (IoC) এবং Dependency Injection (DI)।
* কন্ট্রোলার নিজে কখনো `new EventsService()` করবে না!
* কন্ট্রোলারের কনস্ট্রাক্টরে শুধু টাইপ ডিফাইন করে দেওয়া হবে:
  ```typescript
  // কন্ট্রোলার শুধু বলবে: "আমার একজন EventsService দরকার"
  constructor(private readonly eventsService: EventsService) {}
  ```
* NestJS ফ্রেমওয়ার্ক নিজে ব্যাকগ্রাউন্ডে `EventsService`-এর ইনস্ট্যান্স তৈরি করবে এবং কন্ট্রোলারে ইনজেক্ট করবে।
* এটি নিশ্চিত করার জন্য `EventsService`-এর মাথায় অবশ্যই `@Injectable()` ডেকোরেটর থাকতে হবে এবং `EventsModule`-এর `providers` অ্যারিতে এটি রেজিস্টার থাকতে হবে।
